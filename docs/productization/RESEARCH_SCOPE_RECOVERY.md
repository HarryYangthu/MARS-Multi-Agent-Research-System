# 已封存项目能力的恢复

`bridge/research_scope_recovery.py` 提供主机内部的 `seal_project_scope()` 与 `restore_project_scope()`。它是完整阶段恢复的前置机制，不改变现有研究启动门禁，不创建第二个调度器，也不授予命令、数据或外部网络权限。

已有 `prepare_project_scope()` 仍负责实际源码隔离及知识准备。主机在执行前显式 seal，将候选、源码快照、只读文件范围、排除策略、项目上下文哈希和准备记录哈希写入同一 `run_state.sqlite3` 的不可变扩展。该扩展只保存权限绑定；状态、调用和预算不复制。没有 SQL 封存记录时，磁盘上的普通 scope JSON 不能自行授予恢复权限。

恢复要求已有且身份一致的 StateJournal 与预算账本，交叉核对原请求、冻结合同、源快照、候选标记和 metadata。允许修改范围与保护范围直接取冻结合同，保存的 JSON 不能扩权。路径从当前 run 根和已验证的候选/快照 ID 推导，不采用序列化的任意主机路径。源码快照及 manifest、候选、metadata 均拒绝符号链接或多硬链接文件。

读取不初始化数据库、不建表、不修复投影、不更新用量、不结算未知操作、不复制 live source。原始源目录被移走或删除时，已封存的候选仍可恢复；完整 run 搬迁后的候选路径也实际重建通过。这个局部检查不是整个应用升级/搬迁兼容性验收。文件或身份证据缺失、授权外变更、SQL 行损坏或版本不兼容时拒绝，不能自动重新 seal 后冒充恢复。

## 实际验证

新增 26 项真实文件/SQLite/子进程测试；与原项目 scope 检查联合 **88 passed / 3.14 s**，两文件 strict mypy 通过。覆盖跨进程读取、原源目录移走、真实注册工具修改后的预算保持、metadata/快照/authority/候选损坏、错误 SQL 版本与缺表、跨 run/ledger 混用、扩权拒绝、只读 bytes/mtime 保持和重复 seal。

独立审查曾实际复现旧 snapshot 校验仅检查 hash/mode 而接受外部同字节硬链接的问题。现在对快照所有内容和 manifest 额外验证普通单链接文件；两个原复现均拒绝，测试纳入回归。原先 24 项通过不作为最终覆盖。

另外两个独立真实故障探针验证：实际 Git patch 失败后的 `tool_executions=1` 与两条 unknown 预留在恢复后保持不变；真实 SQLite INSERT 触发拒绝后没有封存行，恢复拒绝，原账本保持不变。没有模型、工具或服务成功替身，没有新增模型或训练调用。日志、源码与独立脚本指纹见 [回执](evidence/research-scope-recovery-checks.json)。

后续仍需把稳定阶段调用身份、产物批准、实际作业所有权与此能力接入同一个 owner；当前还不能把文件能力恢复称为完整研究恢复。
