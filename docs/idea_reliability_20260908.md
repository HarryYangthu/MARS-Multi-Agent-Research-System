# Idea 可靠性迭代与框架选择

截至第十二次真实运行，仍没有同时通过自动验收与独立质量复核的完整方案。目标是自主取得相关论文正文，解释选文和取舍，形成定义完整的方案，并从同一已验收版本输出中文说明和下游结构化交接。下载组件通过、模型审查通过、独立质量复核和科学实验分别记录；下述新修复只记录本批源码与组件验证，后续完整真实运行结果另记。

## 当前修改

- 正文获取使用可配置的连接、无数据等待、完整传输和总时间预算；保留文件大小上限。真实验证配置明确使用 64 MiB，不改变历史运行的 32 MiB 上限。
- 同一 arXiv 论文版本的链接别名共享下载尝试与完整缓存；版本不同不冒充同一内容。每次读取新页段仍生成独立收据。部分传输只记录字节和错误，不进入可引用正文。
- 研究子任务可以提交明确的材料缺口。宿主在已无取证机会且材料不足时停止，不靠报告格式修复填补证据。主 Agent 在委派预算用尽且合格来源不足时也明确停止。
- 正式研究报告增加独立 Reflection，核对实际可见正文、原文结论和迁移推断。新报告的审查状态绑定准确候选和原始 checkpoint；历史报告不被补发审查证明。
- 续跑使用新目录，逐文件核对源档案，保留原失败记录、成功收据、累计预算和未知用量。同源码、同配置且结果已协调的中断才可继续；不会自动重放结果未知的工具。

第十次运行前的整合版本全量后端及 synthetic regression 测试通过（19 项外部条件或指定真实档案测试显式跳过），462 个文件严格类型检查通过，4 条架构边界检查及 20 候选 synthetic smoke 通过。下载、停止和来源续跑的指定真实档案检查另行执行，证据见下文。这些是历史版本的检查结果，不能代替后续修复的回归或完整 Agent 验收。

该次在 1200 秒时中断于第二次方案审查；20 次模型请求有 19 次响应，已知 522,249 token，未返回响应的用量未知。下一次新运行明确申请 1800 秒，脚本允许的总时限上界为 3600 秒；续跑仍检查源运行实际保存的原时限，不给旧运行追加时间。

## 第十二次之后的新修复与验证层次

- 已知 arXiv ID 可通过 `arxiv_ids` 查询真实元数据，可明确 `vN` 版本；不与关键词、过滤或排序参数混用。返回元数据核对请求的论文/显式版本，原始 XML 与哈希归档，缓存再次解析并与保存结果核对，避免用猜测标题或版本拼凑来源。
- 原生文档调用先严格解析模型提供的原始 JSON 参数，错误行列指向原文本；重复键、非有限数和非法字段继续拒绝，不自动补全或执行错误提交。
- 引句匹配仅增加受限的真实 PDF 单行断词处理：需原页存在符合条件的行末连字符，不能跨空段、删行内连字符或改变数学符号。原引句、原页和收据保持原样，记录匹配模式及原页位置。排版匹配通过不代表论文结论成立。
- 子任务运行或关闭 provider 时的异常保留 `delegation_id`、失败类型和可用 checkpoint 信息，失败材料不计为已接受来源；主 Agent 按真正接受的报告核算后续缺口。研究提示与审查要求区分作者方法、背景基线及尚未实际读到的方法段。
- 正式 Idea、研究子任务及真实验证场景的输入预算改为 256,000，通用策略仍有 512,000 硬上界。这里是 UTF-8 字节形成的保守 token 上界，不是 provider 实测 token；旧 96,000 保护可阻止实际能装入模型的审查输入。[DeepSeek 官方模型说明](https://api-docs.deepseek.com/quick_start/pricing/)列出 Flash/Pro 的 1M context，本次仍使用较小的显式预算。配置变更影响指纹，不能自动恢复旧预算运行。

新 arXiv 入口已通过真实注册工具查询 `2404.19756v1` 与 `2511.01433v1`，返回两个准确版本并复核缓存，记录在 `runs/verification/arxiv_exact_20260908T170534Z/`。它只验证检索组件，材料没有注入新的 Idea 上下文。对第十二次第三个子任务原档案重建完整审查输入，估算为 116,832 / 256,000，四项完整阅读 Observation、候选和任务均保留，无历史压缩或省略；这是离线装载检查，没有调用模型、补发 Reflection 或接受旧报告。

本批在隔离工作树完成全量回归：1,666 项通过、22 项显式条件跳过，耗时 175.03 秒；原生参数与断词的指定真实档案检查已启用。第十二次实际输入超限档案与 arXiv 合同另行合并执行 26 项检查通过，不与全量数量相加。严格类型检查覆盖 468 个文件，4 条架构依赖检查及差异格式检查通过。`docs/evaluation/idea_quality_20260908/verification.json` 已汇总十二次真实终态，先前已归档的 121 项哈希保持不变。本批源码检查通过；后续完整真实运行结果另记。这些检查没有执行新的模型语义审查、独立质量验收或双重交付。

## 验收顺序

1. 用实际失败来源验证下载、缓存、错误分类和有限重试；用真实旧档案检查停止条件与续跑拒绝条件。
2. 从干净提交启动当前二维 LUT 任务，由 Agent 自主选择至少两篇论文的方法页段。必须通过研究报告审查、方案审查、独立质量复核及双重交付一致性检查。
3. 在不同任务约束下继续真实验证，并分别记录正常交付与材料不足时正确停止的结果。小规模通过记录不被解释为对任意问题的成功保证。
4. 保留实际方案、原始模型输出、来源页段和审查意见。性能是否提升由后续实验回答，Idea 阶段不得提前声称。

## 是否现在迁移 LangChain / LangGraph

建议本轮保留现有执行器。MARS 已声明 LangGraph 依赖，但 Idea 实际经 `BaseAgent → NativeAgentLoop` 执行；Bridge 的 LangGraph facade 只编译占位流程并记录清单，没有配置持久化 checkpointer 或调用该图完成 Idea 循环。依赖或配置标签不能当作已有持久化执行。

LangChain 提供模型、工具、Agent 和结构化输出适配；LangGraph 提供更底层的有状态编排、持久化和人工介入，也可独立于 LangChain 使用。参见 [LangChain 概览](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph 概览](https://docs.langchain.com/oss/python/langgraph/overview) 和 [结构化输出](https://docs.langchain.com/oss/python/langchain/structured-output)。

本轮主要问题是正文获取策略、资源身份与重试预算、原生提交协议、完整审查输入预算、材料不足的停止规则、论文理解和方法定义。这些业务与证据要求仍需在 MARS 内实现和验收。第十一、十二次及单次模型比较没有提供迁移框架即可解决这些问题的证据。直接迁移会同时改变执行路径和故障处理，使修复效果更难归因，并需要重新验证 Gate、收据哈希、旧档案和累计用量。

当跨进程恢复、多分支调研及长时间人工审阅成为持续开发负担时，优先做一个可切换的 LangGraph 适配器，保留 NativeAgentLoop 基线，用相同任务比较。持久化状态应只有一个权威来源；工具执行继续经过 MARS 注册中心与 Gate。LangGraph 恢复依赖 checkpoint 边界，部分步骤可能重放，因此幂等处理、未知结果核对和持久化后端仍需设计。参见 [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

模型、检索策略、输出合同和执行框架应分别比较，以便保留可解释的基线。LangChain 仅在具体适配需求出现时引入，不作为当前质量闭环的前置条件。
