# Idea 调研质量与双重交付

目标是交付有来源依据、解释清楚、可交给实验环节验证的方案。成功调用工具、下载论文、字段非空，都不足以证明调研有用。

## 从研究问题到方法决定

当前正式委派调研提交包含 `research_assessment`（版本 `idea.research_assessment.v1`）：

| 字段 | 要回答的问题 |
|---|---|
| `task_question` | 本次要解决什么具体问题？ |
| `selection_principles[].criterion / task_basis` | 按什么原则选文，这条原则对应哪个任务约束或信息缺口？ |
| `source_decisions[].decision` | 对已取得可用研究结论的每篇文章，最终采纳、排除还是暂缓？ |
| `reason / task_relevance / criterion_ids` | 为什么作此决定，与当前任务、选文原则有什么关系？ |
| `insight_ids / transfer_assumptions` | 采纳哪些思路，迁移成立需要哪些条件？ |
| `stopping_reason / remaining_gaps` | 为什么足以形成当前方案，还缺什么？ |

`research_links` 将真实委派报告中的思路连接到 `method_spec` 的具体定义，并记录迁移理由。报告保留原文引句、页码、阅读收据、文档摘要、论文结论、迁移推断和局限；宿主从实际工具记录重验这些来源。

仅因关键词相同、引用量高或容易下载，不能据此认定论文有用。可以采用相邻领域的方法，但必须说明任务机制的对应关系、成立条件及不能直接迁移的结论。否定性结论也可以支持一个真实的方法取舍；不能添加无实际作用的字段凑篇数。

每个委派围绕一个具体信息缺口设置所需材料，总篇数在主 Agent 汇总时计算。论文不必已经解决完整目标任务；要证明具体机制为何可以迁移，并将适配成本计入方案。检索服务限流时切换已开放的来源，不把反复换关键词当成补救；空知识库不应重复占用阅读预算。真实验证配置同时开放 OpenAlex 和 arXiv，备用通道仍须留下真实检索与阅读记录。

实验配置 `experimental_research_pro_per_insight_v4` 在 v3 基础上只为调研子 Agent 增加自研 `search.cvf_search`，模型、审查模式及内部预算不变，旧配置的工具集合保持原样。该工具按指定 CVPR、ICCV 或 WACV 年份的官方目录匹配短标题关键词，再从真实论文页面的 citation 元数据取得 PDF 链接；不猜论文地址，也不依赖通用搜索服务的 API key。第一版支持 `/content/{venue}{year}/` 页面结构，旧目录布局会明确拒绝；年份参数范围不代表所有年份都已支持或实测。

CVF 目录、论文页面和请求结果均归档并校验摘要，证据索引重新解析原页面确认标题与 PDF 的关系。只取得元数据不能满足正文阅读门槛，仍须通过 `search.fetch_sources` 获取可验证的 PDF 阅读收据。默认元数据总限时 60 秒、目录上限 8 MiB、单论文页上限 256 KiB；网络访问仍要求显式允许 CVF 域名。宿主把有效子配置的只读工具范围传至真实工具入口，模型参数不能扩大权限。来源可达性与引用相关性分开验收，不能因新通道更易下载而自动采纳其中论文。

## 验收分层

1. **来源与结构**：核对真实阅读收据及文档摘要、论文与思路身份、原则引用、逐篇决定覆盖、思路到方法的有效引用。采纳集合必须与实际方法链接一致，排除或暂缓文章不得同时用作方法依据。新合同的最低来源数只统计实际链接的不同论文；同论文不同版本或重复委派不会增加篇数。
2. **独立上下文模型审查**：检查文章与任务是否相关、节选是否支持结论、迁移条件是否合理、是否存在装饰性引用，以及中文概括是否与规范方法一致。审查收到与写作相同的完整任务和宿主要求，并检查相同消融、域内无效改动、遗漏评估尺寸及初始化额外标签。默认 Idea 开启高推理强度的 Reflection；要求研究档案却关闭审查的配置在调用模型前明确失败。
3. **实验验证**：尚未发生。结构检查和模型审查均不能证明方法有效、新颖或理解一定正确；这些结论需要下游实验和必要的人工评审。

审查必需的真实工具记录按完整内容装载，保留原文页段及调用说明，不用截短内容或仅含地址的索引代替。若完整材料与任务、候选一起超过容量，则在调用审查模型前失败。审查没有工具调用权限，因此不为未发送的工具定义预留容量。

模型的思考与可见输出共用输出上限。正式 Idea 预留 32,768 输出 token；360 秒是流式 SDK 的超时配置，包括等待流数据，不是整次生成的墙钟上限。第十六次冻结版本的作者外层期限为 726 秒，ReviewPlan 审查关闭重试，外部驱动另设 3600 秒总预算；这些限制不能相互替代，详见 [API 记录](evaluation/idea_quality_20260908/api_verification_20260909.json)。耗尽上限不是审查通过，仍必须在有限修复预算内返回完整结构化判断。

原生调用格式错误时，修复请求完整保留原始参数；仅缩短随调用附带的长说明，并明确标记截断、长度及摘要。已有候选、未解决问题和无工具调用的审查正文保持完整。原始响应留在档案中，不自动修补 JSON 或执行被拒绝的调用。

检索命中、下载文件、读到页段、有可追溯提取、实际用于方案，是不同数量。`research_brief.md` 只统计成功报告中的引用页段来源及方案实际使用来源；完整检索和失败委派的数量另见运行记录。页段阅读不能称为全文阅读。材料不足应保留缺口并失败或修订，不应用无关论文补足门槛。

常驻阅读收据索引保留每页实际显示字符数、该页抽取文本总字符数和完整显示、截断或未知标记，另列所选提取范围内没有显示文本的页码。例如第十九次真实记录的 Fourier 第 6 页只显示 356/4099 字符；后来读取第 7—8 页不会补齐第 6 页。完整显示抽取文本也不代表已理解图表、公式、扫描内容或全文。索引不提供引句或研究结论，当前上下文若缺少对应正文仍需重读。

## 一次接受，两种表达

每个接受版本有独立交付目录，不覆盖先前版本：

| 文件 | 用途 |
|---|---|
| `proposal.md` / `proposal.json` | 相同规范方案的 Markdown/frontmatter 与完整结构化元数据；包含方法、判别规则、交接要求、调研决定和研究链接 |
| `summary.txt` | 一两句中文说明，概括做什么及预期作用；不得把假设写成实测提升 |
| `research_brief.md` | 面向人的问题、原则、逐篇理由、引用页段、提取与迁移、方法位置及未决问题 |
| `research_evidence.json` | 与提案摘要绑定的可信委派报告，保留原结论和使用限制 |
| `acceptance.json` | 分开记录结构检查、研究决定一致性、模型审查和实验状态 |

简短正文与 `human_summary` 保持一致，完整方法仅以规范元数据为准，防止维护两份互相冲突的方法定义。中文研究说明由已接受字段和可信报告渲染，不另让模型补写无法追溯的结论。

下游仍以批准后的方案为输入。包含新版调研决定的批准方案会附带 `idea.research_handoff.v1` 上下文包，携带重新核对过来源的研究证据；批准或手工修改不被当成原候选已通过模型审查的证明。未提供真实基线和数据时，交接必须将这些列为执行前提。

## 多场景和不同架构的交接

`evaluation_protocol.arms.baseline/candidate` 与 `comparison` 保留主比较。其他目标场景和消融使用额外具名训练臂，每个臂绑定具体方法、训练/评估数据、目标、初始化及优化器；每个种子下分别训练，不把不同目标的数据混成一次拟合。`comparisons` 逐组指定两臂和规范 `decision_rule` 中的判别过程。宿主对每组检查引用、共同评估集，以及声称隔离架构时的共同训练数据和目标。

`parameter_budget.evaluation_cases` 的尺寸变体默认继承主账本。冻结部分参数、低秩因子等不同候选架构，须同时显式提供该配置的 `candidate_formula` 与完整 `candidate_components`；变量包含全部主变量及新增变量，原基线账本和宿主参数比例上限仍适用。必须另外保留未覆盖的主配置，不能只改申报数字、隐藏张量或省掉主方案检查。账本通过只证明声明的算术一致，仍需审查方法定义是否与之对应。

## 历史兼容与验证边界

历史 `proposal.v1` 保持可读。离线审计只有在当前候选摘要对应的验证记录声明 `research_assessment_required=true` 时，才要求新版决定和双重交付文件；不会用新规则给旧运行补发质量证明。

自动测试使用纯合同输入、真实临时文件和真实配置。它们验证身份、链接、数量、文本一致性及失败边界，不用模型或工具替身宣称一次研究成功。真实论文验证通过 `scripts/run_idea_research_live.py` 另行执行，记录实际来源和全部委派消耗；该脚本属于开发时直接调用 Idea 的入口，不能据此声称工作台端到端验收或真实项目仿真已完成。

## 当前是否接入 LangChain / LangGraph

当前先不迁移 Idea 主循环。已经出现的主要失败是正文不可达、模型动作格式错误和结论超出实际阅读范围；这些问题需要修复来源、协议反馈和证据审查，不能由替换编排框架自动解决。现有 NativeAgentLoop 已管理工具权限、预算、事件、检查点与审查状态，迁移会增加一套待验证的执行语义。

仓库虽然声明了 LangGraph 依赖，现有 `bridge/langgraph_runtime.py` 主要编译拓扑、记录运行清单与事件；其节点为 passthrough，没有配置持久化 checkpointer，也没有把完整 Idea 调研循环交给图执行。因此依赖存在和清单落盘不代表跨进程恢复已经实现。LangGraph 的持久化和中断能力适合未来需要跨进程恢复、多分支汇合、长时间人工审核时，以可切换适配器接入，并保留一套权威状态、工具幂等性及未知执行结果核对。[官方概览](https://docs.langchain.com/oss/python/langgraph/overview)、[持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)。

LangChain 可以在出现明确的模型或工具适配需求时局部采用；LangGraph 可独立使用，不必同时迁移两者。引入前后应使用相同任务和来源门槛比较交付质量、耗时、成本及失败恢复，保留原执行路径作为对照。[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview)。
