# Token 统计与上下文压缩规则

## 2026-10-12：代码材料复用与当前部署配置

本节更新优先于下方历史记录。当前输入预算保留 128,000；它是触发压缩的目标预算，受保护证据超出时仍会保留，由供应商执行实际模型窗口限制。提高输出上限不会扩大配置的输入预算。本次优化没有改动模型、输出额度、审批或原始运行记录。

- `configs/context.yaml` 的 `repository_materials` 控制缓存开关、单文件存档上限、读取索引条目上限和重复读取提示阈值。缓存上限仅决定是否保存额外快照，不拒绝正常文件读取。
- `code.repo_reader` 仍先校验项目目录、允许路径和文件类型，再读取当前字节、计算内容哈希。未提交修改、相同大小/时间戳的改动、换行变化和文件删除都会重新核验；不以 Git 提交号或 mtime 代替内容校验。
- 同一任务的 Agent 共用 `context/repository/` 版本索引及 `context/materials/` 原文快照。索引绑定仓库、相对路径和字节哈希；读取结果仍携带真实正文和字符范围。大文件或关闭缓存时直接读取。历史版本保留，缓存损坏明确失败。
- `cache.material_ref` 可通过 `context.read_material` 按源文件字符偏移取回正文。这是历史快照；需要核对当前工作区时仍调用 `code.repo_reader`。缓存主要减少重复存档及入模内容，不宣称免除文件读取或将磁盘缓存等同于模型记忆。
- 上下文打包按仓库、路径、文件版本、读取范围和正文识别重复片段。仅在本轮提示中确有完整原文时才输出短引用；原文被卸载后，下一份可见正文自动成为完整副本，不出现悬空引用。调用 ID、调用参数和返回配对保持不变，最新一批证据继续受保护。
- 保留稳定的规则与已有消息顺序；把读取范围索引放在历史之后。显示索引合并相同版本/片段的成功读回执，保留次数和首末原始引用；完整逐次记录仍在原 trace。失败、不同版本和不同片段不合并。索引仅说明历史读取范围，不表示当前正文可见或整个文件已经被理解。
- 多次读取同一片段会提示核对目的，但不禁止必要复查、不减少调用计数、不代替科学评审。可在同一任务内跨 Agent 复用原文；不共享 Agent 的结论或审批。

实现借鉴稳定前缀、增量上下文和按需读取原则；没有接入 OpenAI 的专有 compaction，也不保证 DeepSeek 命中供应商侧缓存。参考：[Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)、[Prompt Caching 201](https://developers.openai.com/cookbook/examples/prompt_caching_201)。

验证使用真实临时仓库及历史失败 trace，覆盖跨 Agent 复用、版本变化、失效、原文回读、损坏检测、上下文内去重和原文被卸载后的恢复。历史回放不等于完成研究任务。

2026-09-29，根据自部署模型的使用方式更新。

## 累计用量

`configs/model_usage.yaml` 的 `token_usage_mode: statistics_only` 对全部角色生效，覆盖普通运行账本、冻结合同的研究账本及 Discovery 调研账本。累计输入、累计输出、累计总 token 不再拒绝后续调用。历史合同、配置指纹和用量记录不改写、不清零；新收据记录当前统计模式，结果 API 返回该模式。

供应商返回的真实 token 用量与缺少完整回执时的保守预留分别记录。未知用量不是零。旧合同和资源配置中的 token 总额仅保留作历史参考；在统计模式下不执行这些累计上限。单次输入/输出容量仍用于防止请求超过模型窗口。调用次数、并发、作业时间及其他资源策略独立于累计 token；Coding 的 completion-driven 模式另外取消其固定执行配额。

## 每次模型调用前的容量检查

当前运行使用 runtime context v3。已配置实际模型窗口时，可用输入容量直接为模型窗口减去本次最大输出预留和安全余量，不再受旧 Agent 或运行策略中的 24K/48K 等额外上限约束。未配置实际窗口的模型仍采用保守回退，不能当成无限容量。工具定义也计入输入占用。

用户确认部署窗口为 128K，配置保守按 `model.context_window: 128000` 处理；输入策略上限同时为 128,000。当前单次输出预留 8,192、安全余量 2,048，因此可用输入空间为 117,760。窗口值来自用户确认，并非服务端实测；输出预留改变时可用空间随之变化。

- 占用达到可用输入容量的 **80%** 时触发压缩。
- 压缩目标为可用输入容量的 **65%**，为接下来的工具返回与上游交接留出空间。
- 按当前 117,760 的有效输入容量，触发值为 94,208，目标值为 76,544。这些是 UTF-8 字节保守上界估计，不冒充服务商实测 token 数。
- 压缩顺序：完全重复材料 → 旧工具输出/日志 → 旧过程记录 → 可选代码和背景 → 上游明确标记为可选的背景部分。同类优先处理旧内容。
- 固定规则、用户当前目标、项目约束、未解决错误/审查意见、最新相关工具交互等受保护。未知结构的上游正文默认受保护；工具调用与返回成对保留。
- 先保留摘录和原文引用，再必要时仅保留引用。原文按内容哈希落盘，Agent 可通过 `context.read_material` 分页回读。引用不代表已经完整阅读。
- 这是可恢复的结构裁剪/卸载，不是另一次模型调用生成的语义摘要。没有可用原文回读工具时，不卸载材料。
- 若受保护内容使占用无法降到 65%，但仍在容量内，可以继续；若仍超过输入容量，则不发送请求，报告保护内容和工具定义的占用，要求拆分任务或校准已验证的模型窗口。不能通过丢弃任务要求强行压缩。
- 保存每次压缩前后占用、顺序、材料引用和状态；恢复时重用相同材料和压缩状态。旧 v2 检查点不自动改写成 v3。

## 验证范围

真实临时账本验证全部角色超过累计 token 阈值后仍可记账，冻结合同在不修改合同与历史记录的前提下允许超出累计 token 总额；单次上下文容量仍拒绝超大请求。原有有限额度模式显式测试保留。压缩测试覆盖 80% 边界、65% 目标、保护内容、原文回读与状态恢复。没有用模型替身或伪造研究成功验证此策略。

当前失败 Coding 任务及关联对话的 v3 策略已按用户确认显式增加输入容量，旧策略和调整理由单独归档。既有检查点、材料与压缩历史保持不变；旧检查点指纹不会被绕过，新容量通过新的阶段尝试生效。其他历史任务仍保留自己的策略快照。

最终检查：266 项相关测试通过，667 个文件的严格 mypy 检查通过，四条依赖方向约束通过。本地结果 API 返回 `statistics_only`，当前失败任务账本的 SHA-256 与调整前一致。后端在确认全部 15 个任务和 4 个对话空闲后重新加载。当前任务仍因缺少可写实验副本而阻塞，未自动执行模型或仿真。

后续修复：Focused Idea 曾因独立配置仍为 48,000 而拒绝 51,346 的待发送上下文。现在 v3 作者、评审单元及评审最终打包统一按实际模型窗口计算。真实运行配置核对：即使 Focused 配置仍写 48,000，有效输入容量也为 117,760。34 项上下文、循环及 Focused 运行测试通过；本次没有重跑研究或声称文章阅读完成。
